# Phase 2 status — the Web read model comes from the provenance system

> Written 2026-09-05. P1 (`docs/P1_STATUS.md`) built the evidence core and
> proved every displayed edge traces back to it. P2's own goal, stated by
> the user at hand-off: stop "treating legacy JSON plus sidecars as the
> long-term data architecture" and instead **generate** the edges the Web
> app displays **from** the provenance system. This document covers P2's
> first (and so far only) increment.

## What changed

Before P2, `web/`'s edge data (judgment dependencies, morphisms, typed
concept relations) was generated by `mathesis-graph`/`mathesis-taxonomy`'s
own exporters, reading straight from their SQLite tables. `mathesis-provenance`
only added a thin, optional "sidecar" (`judgments.provenance.json`,
`taxonomy.relations.provenance.json`) that mapped each legacy edge to an
assertion id — the browser had to fetch both files and join them by hand
to show provenance, and if the sidecar was missing, the page fell back to
showing the edge with no provenance annotation at all.

P2 inverts this for the three edge collections `web/` actually displays:

- `crates/mathesis-provenance/src/web_export.rs` (`mathesis-provenance
  web-export --db <path> --release <tag> --out-dir <path>`) reads
  **only** the `ProvenanceStore` — via
  `ProvenanceStore::list_assertions_for_release`, it never opens
  `mathesis-graph`'s or `mathesis-taxonomy`'s SQLite databases — and emits
  `dependencies.json`, `morphisms.json`, `relations.json`.
- Fields the legacy exporters used to read straight off `mathesis-graph`'s
  `morphisms` table or `mathesis-taxonomy`'s `RelationStatus`
  (`kind`/`origin`/`status`/`rationale`/`confidence`) are instead
  reconstructed from the assertion's own `Evidence`/`ReviewDecision` rows —
  see `web_export.rs`'s `build_morphism_edges`/`build_relation_edges` and
  their unit tests. This means the web read model can never disagree with
  what `mathesis-provenance verify` has already checked, because both read
  the same rows through the same logic (`evidence_details_for`/
  `review_decision_details_for` in `assertion_export.rs` are shared by
  `web_export.rs` and the `assertions.json` detail-panel export).
- `web/src/proofGraph.ts` and `web/src/dynamicTaxonomy.ts` fetch these three
  files directly, instead of reading `dependencies`/`morphisms` out of
  `judgments.json` and instead of fetching `taxonomy.relations.json` plus a
  provenance sidecar. `mathesis-graph::export::GraphExport` and
  `mathesis-taxonomy`'s CLI no longer produce `dependencies`/`morphisms`/
  `taxonomy.relations.json` at all — `judgments.json`/`taxonomy.json` are
  now node-data-only (judgment statements, papers, concepts, clusters,
  search index), and edges are exclusively the provenance system's output.
- Because each edge now carries its own `assertionId` from the moment it's
  generated, the client-side code that used to reconstruct a lookup key to
  join against the sidecar (`web/src/dynamicTaxonomy.ts`'s
  `lookupRelationProvenance`, `web/src/proofGraph.ts`'s
  `morphismProvenance` map) is gone — the assertion id is just a field on
  the object already being rendered. The "provenance" button/icon on every
  morphism chip and every typed relation is now unconditional, because
  there is no longer a case where the edge exists but its provenance link
  is missing.
- A real, substantive correctness fix fell out of this for free: the old
  `taxonomy.relations.json` exporter hardcoded `confidence: 1.0` for every
  `Grounded` relation (a rendering placeholder, not a measurement —
  `relations.rs::merge()`'s `Grounded` branch never touched `confidence`).
  `relations.json`'s `confidence` field is `null` for `Grounded` relations
  now — there is no distributional score to report, so none is invented.
  `Confirmed` relations keep their real, measured `invCL` value.

## What this increment does NOT do (deliberately, matching the user's own
## "what I would not do yet" list from the P1 follow-up)

- **Node data is still generated by the legacy exporters.** Judgment
  statements, contexts, papers, concept clusters, and the search index are
  not part of the evidence core's schema (`SourceRecord`/
  `RelationAssertion`/`Evidence` model *relations between things*, not the
  things themselves) — building a typed entity catalog for them is
  ARCHITECTURE_NEXT.md §5.2's explicitly-deferred work, not this increment.
- **`assertions.json` (the full per-assertion detail panel) is unchanged.**
  `dependencies.json`/`morphisms.json`/`relations.json` carry only the
  display-critical *derived* scalars (status/origin/confidence/etc.), not
  the full `Evidence`/`ReviewDecision` arrays — those still live in
  `assertions.json`, fetched lazily on click, to avoid shipping the same
  evidence text in four different files.
- **`reconcile`/`verify` are untouched.** They still walk the legacy
  databases to re-derive `legacy_ref` keys and check that every currently-
  displayed edge resolves — this is a *different* concern (auditability:
  "does this release's data honestly trace back to its inputs") from
  `web-export`'s concern (serving: "what should the browser show"). Both
  read the same `ProvenanceStore`, so they cannot silently disagree, but
  deleting one in favor of the other was not attempted.
- **No new heuristic extractors, no graph database, no vector search, no
  curator workflow, no UI redesign** — same boundary P1 drew.
