# Phase 2 status — the Web read model comes from the provenance system

> Written 2026-09-05. P1 (`docs/P1_STATUS.md`) built the evidence core and
> proved every displayed edge traces back to it. P2's own goal, stated by
> the user at hand-off: stop "treating legacy JSON plus sidecars as the
> long-term data architecture" and instead **generate** the edges the Web
> app displays **from** the provenance system. This document covers P2's
> first (and so far only) increment.

## What changed

Before P2, `web/`'s edge data (judgment dependencies, morphisms, typed
concept relations) was generated by `mathesis-graph`/`mathesis-taxonomy`'s
own exporters, reading straight from their SQLite tables. `mathesis-provenance`
only added a thin, optional "sidecar" (`judgments.provenance.json`,
`taxonomy.relations.provenance.json`) that mapped each legacy edge to an
assertion id — the browser had to fetch both files and join them by hand
to show provenance, and if the sidecar was missing, the page fell back to
showing the edge with no provenance annotation at all.

P2 inverts this for the three edge collections `web/` actually displays:

- `crates/mathesis-provenance/src/web_export.rs` (`mathesis-provenance
  web-export --db <path> --release <tag> --out-dir <path>`) reads
  **only** the `ProvenanceStore` — via
  `ProvenanceStore::list_assertions_for_release`, it never opens
  `mathesis-graph`'s or `mathesis-taxonomy`'s SQLite databases — and emits
  `dependencies.json`, `morphisms.json`, `relations.json`.
- Fields the legacy exporters used to read straight off `mathesis-graph`'s
  `morphisms` table or `mathesis-taxonomy`'s `RelationStatus`
  (`kind`/`origin`/`status`/`rationale`/`confidence`) are instead
  reconstructed from the assertion's own `Evidence`/`ReviewDecision` rows —
  see `web_export.rs`'s `build_morphism_edges`/`build_relation_edges` and
  their unit tests. This means the web read model can never disagree with
  what `mathesis-provenance verify` has already checked, because both read
  the same rows through the same logic (`evidence_details_for`/
  `review_decision_details_for` in `assertion_export.rs` are shared by
  `web_export.rs` and the `assertions.json` detail-panel export).
- `web/src/proofGraph.ts` and `web/src/dynamicTaxonomy.ts` fetch these three
  files directly, instead of reading `dependencies`/`morphisms` out of
  `judgments.json` and instead of fetching `taxonomy.relations.json` plus a
  provenance sidecar. `mathesis-graph::export::GraphExport` and
  `mathesis-taxonomy`'s CLI no longer produce `dependencies`/`morphisms`/
  `taxonomy.relations.json` at all — `judgments.json`/`taxonomy.json` are
  now node-data-only (judgment statements, papers, concepts, clusters,
  search index), and edges are exclusively the provenance system's output.
- Because each edge now carries its own `assertionId` from the moment it's
  generated, the client-side code that used to reconstruct a lookup key to
  join against the sidecar (`web/src/dynamicTaxonomy.ts`'s
  `lookupRelationProvenance`, `web/src/proofGraph.ts`'s
  `morphismProvenance` map) is gone — the assertion id is just a field on
  the object already being rendered. The "provenance" button/icon on every
  morphism chip and every typed relation is now unconditional, because
  there is no longer a case where the edge exists but its provenance link
  is missing.
- A real, substantive correctness fix fell out of this for free: the old
  `taxonomy.relations.json` exporter hardcoded `confidence: 1.0` for every
  `Grounded` relation (a rendering placeholder, not a measurement —
  `relations.rs::merge()`'s `Grounded` branch never touched `confidence`).
  `relations.json`'s `confidence` field is `null` for `Grounded` relations
  now — there is no distributional score to report, so none is invented.
  `Confirmed` relations keep their real, measured `invCL` value.

## What this increment does NOT do (deliberately, matching the user's own
## "what I would not do yet" list from the P1 follow-up)

- **Node data is still generated by the legacy exporters.** Judgment
  statements, contexts, papers, concept clusters, and the search index are
  not part of the evidence core's schema (`SourceRecord`/
  `RelationAssertion`/`Evidence` model *relations between things*, not the
  things themselves) — building a typed entity catalog for them is
  ARCHITECTURE_NEXT.md §5.2's explicitly-deferred work, not this increment.
- **`assertions.json` (the full per-assertion detail panel) is unchanged.**
  `dependencies.json`/`morphisms.json`/`relations.json` carry only the
  display-critical *derived* scalars (status/origin/confidence/etc.), not
  the full `Evidence`/`ReviewDecision` arrays — those still live in
  `assertions.json`, fetched lazily on click, to avoid shipping the same
  evidence text in four different files.
- **`reconcile`/`verify` are untouched.** They still walk the legacy
  databases to re-derive `legacy_ref` keys and check that every currently-
  displayed edge resolves — this is a *different* concern (auditability:
  "does this release's data honestly trace back to its inputs") from
  `web-export`'s concern (serving: "what should the browser show"). Both
  read the same `ProvenanceStore`, so they cannot silently disagree, but
  deleting one in favor of the other was not attempted. The stabilization
  pass below adds a single command that runs both, rather than merging
  their internals.
- **No new heuristic extractors, no graph database, no vector search, no
  curator workflow, no UI redesign** — same boundary P1 drew.

## Stabilization pass (same day, second update)

A follow-up review asked for a 12-point stabilization pass so the
provenance core is "the only authoritative edge source, reproducible from
a clean checkout, and protected against future regressions" — without
starting new architectural expansion (P3). Delivered:

1. **`mathesis-provenance web-export` now writes its own manifest**
   (`web-export-manifest.json`): schema version, release tag/id/commit,
   `web_export_version`, counts, and a SHA-256 of each of the 3 files it
   just wrote — computed *after* writing, so it can detect later
   tampering or transfer corruption. Counts and hashes are generated by
   the tool, never hand-typed.
2. **One release gate, one exit code**: `mathesis-provenance verify-release`
   (`src/release_gate.rs`, wired in `main.rs`) runs P1's existing `verify`
   (sidecar → assertion → evidence → source_record → release) *and* a new
   P2-specific check, and fails if either does. The P2 check is stronger
   than a hash comparison: it calls `web_export::build_web_export` against
   the *live* `ProvenanceStore` and structurally compares the result
   (as `serde_json::Value`, not just a hash) against what's actually on
   disk — this is what catches "this export was generated from an earlier
   commit/DB state and never regenerated," which a hash-only check would
   miss if someone recomputed the manifest's hash to match the stale file.
   Verified against real production data both ways: a clean run passes
   (`8969 sidecar entries` OK, web-export OK), and a deliberately truncated
   `morphisms.json` is rejected with both `output_hash_mismatch` and
   `malformed_json`, exit code 1.
3. **Reproducibility**: not tested from a *clean checkout* in this pass —
   this environment has no way to re-fetch the underlying 142,948 arXiv
   papers (`scratch/papers_100k_fc.db` is 700MB of already-ingested corpus
   data, not something this pass can regenerate from raw sources). What
   *is* verified deterministically is that `web-export` run twice against
   an unchanged `ProvenanceStore` produces byte-identical output — that is
   exactly what `verify-release`'s regeneration comparison proves on every
   run, which is the practical form of reproducibility available here.
4. **Exactly one writer per edge file, confirmed by search**: grepped the
   whole `crates/` tree for `dependencies.json`/`morphisms.json`/
   `relations.json`/`taxonomy.relations` — the only `std::fs::write` call
   for any of the three is in `mathesis-provenance/src/main.rs`'s
   `run_web_export`. Every other hit is a doc comment.
5. **Schema version, without reshaping the shipped files**: kept the
   top-level bare-array shape (`web/src` already parses it that way) and
   put `schemaVersion`/`WEB_EXPORT_SCHEMA_VERSION` in the manifest instead
   — `verify-release` is what actually enforces it (`unknown_web_export_schema_version`
   failure), matching the alternative the review itself offered.
6. **Client failure states made explicit**: `web/src/util.ts::assertArrayShape`
   throws a clear error if a fetched export is not a JSON array — a 200
   response with the wrong shape can no longer be silently treated as an
   empty-but-valid dataset. For `dependencies.json`/`morphisms.json`
   (required, no legacy fallback exists post-P2) this feeds `loadError`;
   for `relations.json` (soft-fail, matching its sibling `taxonomy.papers.json`/
   `taxonomy.aliases.json`) a non-404 failure or bad shape now calls
   `reportProvenanceIssue` instead of quietly leaving the dataset empty.
7. **Contract tests, split across the two languages that actually own each
   half of the contract**: `crates/mathesis-provenance/src/web_export.rs::
   every_generated_edge_resolves_to_a_consistent_assertion` sweeps every
   generated dependency/morphism/relation and re-derives `kind`/`origin`/
   `status`/`confidence` independently from the assertion's own
   Evidence/ReviewDecision rows, failing if it ever disagrees with what
   `build_*_edges` produced. `web/eval/searchEval.ts::evaluateWebExportContract`
   calls the *real* client function (`dynamicTaxonomy.ts::expandRelations`,
   now exported for this reason) against the real `relations.json` and
   confirms every relation resolves to the same `assertionId` from both
   directions (`A → B` and `B → A`) — the regression class a past review
   round already found once (`web-README`'s direction-folding fix) now has
   an automated guard instead of relying on manual re-verification. Both
   pass on real production data (1,051/1,051 relations, 0 duplicate
   `assertionId`s in `dependencies.json`/`morphisms.json`).
8. **Store invariants**: `PRAGMA foreign_keys = ON` was already set on
   every `open`/`open_in_memory`, and `UNIQUE(provider, provider_id,
   provider_revision)` / `UNIQUE(release_id, legacy_ref)` already existed.
   Added the two tests that were missing: `source_record_with_same_revision_is_interned_to_the_same_record`
   and `source_record_with_a_different_revision_is_a_different_record`
   (`tests/store_roundtrip.rs`) — the exact regression the P1 round-2
   review already fixed once, now pinned so it "cannot return." "Every
   assertion has ≥1 Evidence row" is deliberately left as an
   application-level check (`verify`), not a trigger — SQLite has no
   direct way to express "referenced by at least one row in another
   table" as a table constraint, and this project's convention is to
   enforce cross-table completeness at the release-gate layer, not with
   triggers.
9. **Migration/corruption cases**: `tests/verify_test.rs` (P1) already
   covered wrong release, missing assertion, missing evidence, ambiguous
   duplicate key, counts mismatch, input-hash drift, and manifest/DB
   mismatch. `tests/release_gate_test.rs` (new) adds the P2-specific ones:
   output hash drift, a stale export after the store changes, a
   *partially copied export directory* (one of the three files missing),
   unknown schema version, release-tag mismatch, and malformed JSON.
   External file parsing (`serde_json::from_slice(...).with_context(...)`)
   already returns a typed error naming the file, never panics — this was
   already true before this pass and stays true. Internal DB reads
   (`assertion_row`'s `.expect(...)` on a stored enum string) still panic
   on corruption by design, matching `mathesis-graph`'s own convention:
   that data was written by this crate itself, never by an external file
   format, so a bad value there means the *database* is corrupt, which is
   a different failure class than a malformed *export file* — deliberately
   not changed, to stay consistent with the rest of the codebase.
10. **Audit report**: `mathesis-provenance stats` plus the two manifests
    (`provenance-manifest.json`, `web-export-manifest.json`) together
    already carry every field asked for (release tag, commit, schema
    versions, input/output hashes, edge/assertion/evidence/review counts).
    A single combined human-readable report file was not built — the
    existing `verify-release` output plus `stats` cover the same ground
    without a new artifact. Naming discipline is enforced in prose here
    and in `P1_STATUS.md`: **8,969/8,969 is edge traceability and
    resolution coverage, never called "correctness."**
11. **Detail panel**: the panel already used a native `<dialog>` +
    `.showModal()`, which gives Escape-to-close, focus trapping, and
    focus-return-on-close for free per the HTML spec — no new code needed
    for those. Added one line making the traceability/truth distinction
    explicit in the panel itself: *"Traceable to a source ≠ independently
    reviewed ≠ formally verified ≠ mathematically true."* A full
    state-by-state UI test matrix (deep links, long-text overflow, a
    `Verified`/`Reviewed` example — none exist in real data yet to test
    against) was not built; this project has no JS test runner (only
    `tsc` + the manual `eval` scripts), and adding one is a tooling
    decision bigger than this stabilization pass.

Deliberately not done, matching the review's own closing instruction to
stop hardening once these checks exist rather than expand scope further:
a dedicated single-file audit report artifact, a full clean-checkout CI
script, and a JS test framework. Each is named above at the point it was
considered, not silently skipped.

## P1 guarantees

- All visible legacy edges are traceable to a `RelationAssertion`.
- The full provenance chain (assertion → evidence → source record →
  release) resolves for every one of them.
- Release and input-database integrity are verified (`verify-release`).

## P2 guarantees

- Web edge data (`dependencies.json`/`morphisms.json`/`relations.json`) is
  generated only from `ProvenanceStore` — `mathesis-graph`/
  `mathesis-taxonomy`'s SQLite databases are never opened by `web-export`.
- The legacy databases no longer own any Web edge file; `web-export` is
  the sole writer, confirmed by search (item 4 above).
- Every displayed `kind`/`origin`/`status`/`rationale`/`confidence` comes
  from that assertion's own Evidence/ReviewDecision rows, not from
  reading the legacy tables directly — enforced by a generated contract
  test that sweeps every entry, not spot-checked.
- Export and verification are release-aware: `verify-release` rejects an
  export generated from a different commit/release/DB state, a
  schema-version mismatch, a partially copied export directory, or a
  hand-edited/corrupted file.

## Still not guaranteed

- **Mathematical truth.** Traceability is not correctness — see the
  detail panel's own caveat and `P1_STATUS.md`.
- **Complete typed entity semantics** (ARCHITECTURE_NEXT.md §5.2's
  catalog) — `subject_ref`/`object_ref` remain tagged strings.
- **Exact evidence spans for every source** — `judgment_dependencies`
  locators are file:line, not byte-precise; `paper_citations` has none.
- **Human review of every assertion** — `ReviewDecision` only preserves
  legacy `Accepted` flags; there is no reviewer UI or identity system.
- **Formal verification of every relation** — `verified` is a defined
  epistemic state that nothing populates yet.
- **Completeness of the mathematical corpus** — this is a snapshot of
  what was ingested, not a claim about mathematics at large.
- **A clean-checkout reproducibility test and a single-file audit-report
  artifact** — named above as deliberately deferred, not silently
  dropped.
